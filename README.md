# awg3-panel

**Веб-панель выпуска и редактирования клиентских конфигов AmneziaWG — для тех, кто держит туннель, где цена ошибки равна потере доступа к самому туннелю.**

![Go](https://img.shields.io/badge/Go-1.26-00ADD8?logo=go&logoColor=white)
![Зависимости](https://img.shields.io/badge/внешних%20зависимостей-3%20(вендорятся)-success)
![Размер](https://img.shields.io/badge/RSS-%3C%2030%20МБ-success)
![Тесты](https://img.shields.io/badge/тесты-2%20сборки%2C%207%20пакетов-success)

Один статический бинарь без БД, Docker и Node. Обслуживает один или несколько интерфейсов AWG сразу, правит **только** секции `[Peer]`, применяет изменения через `awg syncconf` и откатывает их сам, если живое устройство после применения разошлось с ожиданием.

---

## Зачем это существует

Выпуск пира в AmneziaWG 3.0 руками — это сгенерировать ключ и PSK, выбрать свободный адрес, дописать блок в серверный конфиг, применить его и собрать клиентский файл со всеми v3-полями обфускации. Каждый шаг воспроизводим, и каждый умеет отказать молча:

| Ошибка | Как проявляется |
|---|---|
| Пропущено одно поле обфускации (`S1..S4`, `H1..H4`, `HeaderProtectionKey`, `ContentPaddingAddition`) | Клиент подключается, шлёт пакеты, получает `0 B`. Никакой ошибки — просто тишина |
| `awg setconf` вместо `awg syncconf` | Рвутся **все** живые сессии, включая ту, по которой ты сейчас работаешь |
| Искажено поле `[Interface]` при перезаписи конфига | Меняется обфускация на живом интерфейсе — молча отваливаются все клиенты разом. `syncconf` при этом возвращает код 0 |
| Конфиг на диске разошёлся с устройством | Следующая правка применит расхождение к устройству, и откат не поможет: он идёт из того же файла |

Панель делает эти четыре ошибки **невозможными по построению**, а не «маловероятными при аккуратности».

## Как устроена безопасность

Любая мутация проходит один и тот же инвариант. Не «желательно», а единственный путь записи в коде:

```
0. снимок состояния устройства         awg show dump + awg showconf
1. чтение конфига как ТЕКСТА           (не пересборка из структуры)
1.5 сверка файла с устройством         разошлись → отказ ДО записи
2. хирургическая правка текста         ровно один блок [Peer], по байтовым границам
3. бэкап                               последние 20 хранятся
4. атомарная запись                    tmp в том же каталоге → chmod 600 → rename
5. применение                          awg syncconf поверх awg-quick strip
6. проверка постусловия                прежние пиры на месте, allowed-ips и PSK те же,
                                       handshake не обнулился, device-параметры совпали,
                                       ожидаемое изменение произошло
7. расхождение → откат из бэкапа       + повторный syncconf + сверка результата отката
```

Три правила, зашитые в конструкцию, а не в дисциплину разработчика:

- **`awg setconf` не существует в кодовой базе.** В интерфейсе `runtime.Runner` физически нет такого метода — вызвать его неоткуда.
- **Секция `[Interface]` копируется побайтово.** Функции записи работают только с диапазонами строк, принадлежащими блокам `[Peer]`; перед записью результат сверяется побайтово. Обратной сериализации модели в файл в проекте не существует.
- **Чужие `[Peer]` тоже неприкосновенны.** Правка одного пира не меняет ни байта в блоках остальных — включая параметры, которых панель не знает, и комментарии, оставленные человеком.

## Что умеет

- **Несколько интерфейсов** одним процессом, переключатель в вебе. У каждого свой конфиг, своё хранилище, свои умолчания.
- **Выпуск пира** по имени: ключи, PSK, свободный адрес из подсети сервера, готовый `.conf` и QR.
- **Правка выпущенного пира**: имя, адрес в туннеле, DNS, маршруты, `PersistentKeepalive`, MTU, endpoint, джиттер `Jc/Jmin/Jmax` и произвольные дополнительные поля AmneziaWG.
- **Ротация ключей** без потери идентификатора, имени и адреса пира.
- **Умолчания интерфейса** правятся из веба, без рестарта сервиса.
- **Отключение и включение** пира с сохранением его PSK и адреса.
- **Клиентский конфиг собирается на лету** — из приватного ключа, живого `[Interface]` сервера, персональных оверрайдов и умолчаний. Файла, который мог бы устареть, не существует: смена обфускации на сервере отражается в конфигах немедленно.

Отдельная сборка `-tags readonly` физически не содержит обработчиков мутаций — её можно выкатить на боевой хост, пока к записи ещё нет доверия.

## Три поля с одинаковым именем, которые легко перепутать

Проект последовательно разводит их в интерфейсе и документации, потому что цена путаницы — молчаливо неработающий клиент:

| Где | Что означает |
|---|---|
| `AllowedIPs` в серверном `[Peer]` | адрес, который получает клиент — в UI «Адрес в туннеле» |
| `AllowedIPs` в клиентском конфиге | какой трафик уходит в туннель — в UI «Маршрутизировать в туннель» |
| `Address` в серверном `[Interface]` | адрес самого сервера, из его подсети выдаются адреса пирам |

## Быстрый старт

```bash
# Кросс-сборка с любой машины: статический ELF, безразличный к glibc целевой системы
make build            # dist/awg3panel
make build-readonly   # dist/awg3panel-readonly — без обработчиков мутаций

scp dist/awg3panel deploy/install.sh root@server:/tmp/
ssh root@server 'bash /tmp/install.sh --dry-run'   # сначала посмотреть, что изменится
ssh root@server 'bash /tmp/install.sh'
```

Панель слушает адрес **внутри туннеля** (`10.0.0.1:8081` по умолчанию) — снаружи её не существует. Слушать `0.0.0.0` запрещено на уровне валидации конфига: с таким значением сервис откажется стартовать.

Подробности — разделы «Установка», «Конфигурация» и «Несколько интерфейсов» ниже.

## Устройство

| Пакет | Ответственность | Побочные эффекты |
|---|---|---|
| `wgconf` | разбор конфига AWG для чтения и хирургическое текстовое редактирование блоков `[Peer]` для записи | нет, чистые функции над строками |
| `store` | метаданные пиров и умолчания интерфейса в JSON | два файла на интерфейс |
| `runtime` | единственная точка вызова `awg` и `awg-quick`; подменяется фейком в тестах | процессы |
| `issuer` | инвариант применения, выбор адреса, сборка клиентского конфига, QR | через `runtime` |
| `web` | роутинг, шаблон, Basic-аутентификация с блокировкой перебора, защита от CSRF | сеть |

Зависимости строго вниз: `web` → `issuer` → (`wgconf`, `store`, `runtime`). Реальный `Runner` подменяется фейком, который моделирует **измеренное** поведение живого `awg` — включая молчаливые отказы: потерю device-параметра, обнуление handshake, подмену PSK. Поэтому логика применения изменений проверяется без живого туннеля.

Внешних зависимостей три, все вендорятся в репозиторий: генерация QR, `bcrypt`, разбор YAML. Всё остальное — стандартная библиотека.

## Методология

Проект написан по конвейеру «спека → план → TDD внутри каждой задачи → верификация». Спеки и планы лежат в [`docs/superpowers/`](docs/superpowers/) и читаются как отдельный документ: там зафиксировано, **почему** принято каждое решение и какой ценой обошлась альтернатива.

Комментарии в коде объясняют причину, а не действие. Многие из них — эпитафии реальным находкам ревью: почему пустая строка-разделитель дописывается только при непустом списке пиров, почему `syncconf` сбрасывает device-поле, отсутствующее во входных данных (измерено на живом сервере), почему проверка публичного ключа при миграции обязательна.

## Чего панель сознательно не делает

Не правит серверный `[Interface]` — ни обфускацию, ни `ListenPort`, ни MTU сервера, ни `PostUp`/`PostDown`. Не управляет systemd-юнитом интерфейса, файрволом и NAT. Не устанавливает и не обновляет AmneziaWG. Не ведёт историю трафика, лимиты и квоты. Не разграничивает пользователей: доступ единый, по одному Basic-логину.

Всё это — осознанные не-цели, а не недоделки. Обоснование каждой — в спеке.

## Что делает и чего не делает

Умеет: обслуживать несколько интерфейсов AWG одним процессом с переключателем в
вебе (см. «Несколько интерфейсов»); список пиров с живым статусом (адрес,
последний handshake, rx/tx); добавление пира по имени — генерация ключей и PSK,
выбор свободного адреса, применение и выдача клиентского `.conf` + QR; правку уже
выпущенного пира — имя, адрес в туннеле, DNS, маршруты, keepalive, MTU, endpoint,
джиттер и произвольные дополнительные поля (см. «Правка параметров пира»); ротацию
ключей пира без потери его идентификатора, имени и адреса (см. «Ротация ключей»);
правку умолчаний интерфейса из веба, без рестарта сервиса (см. «Умолчания
интерфейса»); удаление и временное отключение пира с возможностью включить
обратно; повторную выдачу ранее созданного конфига — он всегда собирается заново
по текущим данным, а не читается с диска.

Сознательно не умеет: **править серверный `[Interface]` ни одного из
интерфейсов** — обфускацию (`S1..S4`, `H1..H4`, `HeaderProtectionKey`,
`ContentPaddingAddition`), `ListenPort`, `MTU` сервера, `PostUp`/`PostDown` и
прочее панель не трогает и не может тронуть по построению (см. «Безопасность
мутаций») — такие правки по-прежнему делаются руками по SSH; управлять
systemd-юнитом интерфейса, его портом на файрволе, правилами NAT; устанавливать и
обновлять AmneziaWG; работать с другими протоколами и маршрутизацией; вести
историю трафика, лимиты и квоты; разграничивать пользователей — доступ единый, по
одному Basic-логину на все интерфейсы сразу.

**`awg setconf` не вызывается никогда и ниоткуда.** Интерфейс `runtime.Runner`
(`internal/runtime/runner.go`) физически не содержит такого метода: есть
`Show`, `ShowConf`, `Strip`, `SyncConf`, `GenKey`, `GenPSK`, `PubKey`, и только
`SyncConf` трогает живое устройство. Причина не в стиле, а в измеренном факте:
`awg setconf` рвёт уже установленные сессии, `awg syncconf` — нет; это
проверено на живом сервере при разработке инварианта применения (раздел 6.1
спеки). Вся запись на устройство идёт только через `syncconf` поверх
результата `awg-quick strip`.

## Две сборки

Бинарь собирается в двух вариантах через build-тег `readonly`:

| | Полная | `readonly` |
|---|---|---|
| Команда | `make build` | `make build-readonly` |
| Файл | `dist/awg3panel` | `dist/awg3panel-readonly` |
| Список пиров, живой статус | есть | есть |
| Добавление/удаление/отключение пира, CLI `add`/`rm`/`disable`/`enable` | есть | **нет** |

В `readonly`-сборке обработчиков мутаций нет физически, а не выключены флагом:
файлы `cmd/awg3panel/cli.go`, `internal/web/handlers_mutate.go`,
`cmd/awg3panel/server_full.go` несут тег `!readonly` и в такой сборке не
компилируются вовсе. Это осознанная этапность выката (раздел 12.1 спеки):
первая версия на боевом сервере физически не могла ничего испортить, потому
что писать было нечем. Какая сборка перед вами — видно из версии:

```
$ awg3panel version
awg3panel <версия> (сборка: полная)
$ awg3panel-readonly version
awg3panel <версия> (сборка: только чтение)
```

## Установка

Сборка — на рабочей машине, кросс-компиляция в статический бинарь, безразличный
к glibc целевой системы. На сервере не нужны ни Go, ни исходники:

```bash
make build            # dist/awg3panel — полная сборка
make build-readonly    # dist/awg3panel-readonly — только чтение
```

Копирование и установка:

```bash
scp dist/awg3panel deploy/install.sh deploy/awg3panel.service deploy/config.example.yaml \
    root@сервер:/root/awg3panel-deploy/
ssh root@сервер
cd /root/awg3panel-deploy
./install.sh --dry-run     # что будет сделано, ничего не пишет на диск
./install.sh                # собственно установка
```

`install.sh` идемпотентен: повторный запуск на настроенной системе не меняет
состояние (бинарь и юнит перезаписываются только при реальном изменении;
существующий `config.yaml` никогда не перетирается). Первый запуск создаёт
каталоги, кладёт бинарь и `config.yaml` из примера, ставит юнит — но **не
запускает сервис**, пока в `config.yaml` не задан bcrypt-хеш пароля (метка
`ЗАМЕНИТЬ`). Хеш получается паролем через pipe, а не аргументом: аргумент
командной строки оседает в истории оболочки, стандартный ввод — нет.

```bash
printf '%s' 'ваш-пароль' | /usr/local/bin/awg3panel hash-password
```

Полученную строку `$2a$12$...` — в `auth.bcrypt` в `/etc/awg3panel/config.yaml`,
остальные поля сверить с таблицей ниже, и запустить установку ещё раз — теперь
она включит и запустит сервис:

```bash
./install.sh
systemctl status awg3panel
```

Откат:

```bash
systemctl disable --now awg3panel
rm -rf /usr/local/bin/awg3panel /etc/awg3panel /var/lib/awg3panel \
       /etc/systemd/system/awg3panel.service
```

Серверный `awg3.conf` при этом не трогается — состав пиров, выпущенных
панелью, остаётся как есть.

## Конфигурация

`/etc/awg3panel/config.yaml`, права `0600`. Загрузка строгая: невалидный
конфиг — отказ старта с внятной ошибкой, а не работа на умолчаниях.

Верхний уровень:

| Поле | Значение | Пример |
|---|---|---|
| `listen` | адрес:порт панели. Обязан быть конкретным адресом **внутри туннеля** — `0.0.0.0`, `::` и пустой хост валидация отвергает | `10.0.0.1:8081` |
| `auth.user` | имя пользователя Basic auth, общий на все интерфейсы | `admin` |
| `auth.bcrypt` | bcrypt-хеш пароля, получить через `awg3panel hash-password` | `$2a$12$...` |
| `interfaces` | список управляемых интерфейсов AWG, см. ниже | — |

Каждый элемент `interfaces`:

| Поле | Значение | Пример |
|---|---|---|
| `id` | slug интерфейса: `[a-z0-9-]{1,32}`, уникален. Часть URL в вебе и значение флага `--iface` | `awg31` |
| `title` | подпись вкладки в вебе; не задано — подставляется `id` | `awg3.1` |
| `interface` | имя устройства для `awg show`/`awg syncconf`, уникально | `awg3.1` |
| `config` | путь к серверному конфигу этого интерфейса | `/etc/amnezia/amneziawg/awg3.1.conf` |
| `bin_dir` | каталог с бинарями `awg` и `awg-quick` для этого интерфейса | `/opt/awg3.1/bin` |
| `interface_edit` | зарезервировано под будущую правку серверного `[Interface]`; в этой версии панели ни на что не влияет — такого кода в бинаре нет (см. «Что делает и чего не делает») | `false` |
| `client.*` | **сид** умолчаний клиента: `endpoint`, `allowed_ips`, `persistent_keepalive`, `dns`, `jc`/`jmin`/`jmax`. Используется только при первом запуске интерфейса — переносится в `defaults.json` и дальше не перечитывается (см. «Умолчания интерфейса») | `endpoint: "203.0.113.10:51820"` |
| `storage.state` | путь к `peers.json` этого интерфейса | `/var/lib/awg3panel/awg31/peers.json` |
| `storage.backups` | каталог бэкапов серверного конфига этого интерфейса | `/var/lib/awg3panel/awg31/backups` |
| `storage.keys` | каталог приватных ключей клиентов этого интерфейса (`0700`, файлы `0600`) | `/var/lib/awg3panel/awg31/keys` |
| `storage.client_configs` | легаси: каталог, куда старая (одноинтерфейсная) версия панели складывала выданные `.conf`. Нужен только на время миграции приватных ключей оттуда в `storage.keys` (см. «Миграция ключей со старой установки»); когда каталог опустеет — поле можно убрать | `/var/lib/awg3panel/clients` |

Пути `config`, `storage.state`, `storage.backups`, `storage.keys` не должны
повторяться между интерфейсами: общий файл означал бы, что согласование
состояния одного интерфейса вычищает пиров другого. Панель проверяет это при
старте и отказывается запускаться при пересечении.

`defaults.json` (а в будущем — и `pending-interface.json`) собственных полей в
`config.yaml` не имеет: он всегда лежит рядом с `peers.json`, в том же каталоге.

Старый одноинтерфейсный формат конфига (секции `awg:`, `client:`, `storage:`
прямо на верхнем уровне, без `interfaces:`) по-прежнему читается и на лету
сворачивается в список из одного интерфейса с `id: default`. Присутствие
одновременно старых секций и `interfaces:` — ошибка старта, а не приоритет одной
формы над другой: если в файле есть обе, панели неоткуда знать, какая из них
действует, и молчаливый выбор был бы правильным только в половине случаев.

`[Interface]` клиентского конфига (обфускация: `S1..S4`, `H1..H4`,
`HeaderProtectionKey`, `ContentPaddingAddition`, `MTU`) в `config.yaml` не
хранится — панель копирует его из живого `[Interface]` сервера при каждой
выдаче, поэтому смена обфускации на сервере автоматически отражается в новых
конфигах.

## Несколько интерфейсов

Один процесс `awg3panel` обслуживает весь список `interfaces` из `config.yaml`
одновременно. Каждый интерфейс полностью независим: свой серверный конфиг, свой
`bin_dir`, свои `peers.json`/`defaults.json`/бэкапы/ключи — правка одного не
может задеть другой ни при каких обстоятельствах, потому что общих файлов между
ними нет и быть не может (см. таблицу выше).

В вебе интерфейсы — это переключатель вкладок в шапке страницы; выбранная
вкладка запоминается в адресной строке, так что на конкретный интерфейс можно
сохранить прямую ссылку. `GET /api/ifaces` отдаёт список интерфейсов с их `id`,
`title`, именем устройства и флагом `interface_edit` — панель показывает вкладку
для каждого элемента этого списка независимо от его настроек.

В CLI интерфейс выбирается флагом `-iface <id>`; без флага команды работают с
первым интерфейсом по порядку в `config.yaml`. Команда `awg3panel ifaces`
печатает список всех интерфейсов — то же самое, что отдаёт `GET /api/ifaces`, но
текстом в терминал:

```
$ awg3panel ifaces
awg3     awg3 (боевой)   устройство awg3      правка [Interface]: нет
awg31    awg3.1          устройство awg3.1    правка [Interface]: нет
```

Значение `interface_edit` из конфига в эту строку тоже попадает, но ни на что не
влияет: кода, который читал бы его для решения «пускать правку или нет», в этой
версии панели не существует — фаза 2 спеки 3.1 (правка `[Interface]` под safe
mode) не реализована, см. `CLAUDE.md`.

## CLI

Панель — основной интерфейс; CLI-мутации — инструмент восстановления на
случай, когда демон (`awg3panel serve`) не работает. Обе формы идут через
один и тот же `issuer.Service` и один и тот же инвариант применения
(см. ниже) — разница только в способе вызова. Правка параметров пира и
ротация ключей через CLI сознательно не выведены: второй вход к тем же
мутациям — лишняя поверхность, пока панель работает и веб-путь доступен.

```
awg3panel [-config путь] [-iface id] serve       запуск HTTP-сервера (по умолчанию); -iface не влияет — сервер обслуживает все интерфейсы сразу
awg3panel [-config путь] [-iface id] list        список пиров, состояние, последний handshake
awg3panel [-config путь] [-iface id] add <имя>   выпустить пира, напечатать клиентский конфиг в stdout
awg3panel [-config путь] [-iface id] rm <id>     удалить пира
awg3panel [-config путь] [-iface id] disable <id> временно отключить пира
awg3panel [-config путь] [-iface id] enable <id> включить обратно ранее отключённого
awg3panel [-config путь] ifaces                  список интерфейсов: id, заголовок, устройство, разрешена ли правка [Interface]
awg3panel hash-password                          bcrypt-хеш пароля (аргументом или из stdin)
awg3panel version                                версия и тип сборки
```

`-config` по умолчанию — `/etc/awg3panel/config.yaml`. `-iface` выбирает
интерфейс для `list`/`add`/`rm`/`disable`/`enable` по его `id` из
`config.yaml`; без флага берётся первый интерфейс по порядку в файле,
неизвестный `id` — отказ со списком доступных. `ifaces` работает без `-iface`
(печатает их все сразу) и одинаково в обеих сборках — в отличие от мутирующих
команд, ей нечего ограничивать. В `readonly`-сборке доступны только `list` и
`ifaces`; `add`/`rm`/`disable`/`enable` отвечают «команда недоступна: бинарь
собран в режиме только чтения» — отдельно от «неизвестная команда», чтобы
опечатка не выглядела осознанным ограничением.

Перед мутацией CLI проверяет, слушает ли уже кто-то `listen`-адрес из своего
же конфига, и если да — отказывает с кодом 4:

```
$ awg3panel add тест
похоже, панель уже запущена и слушает 10.0.0.1:8081 — измените пира через
веб-интерфейс, либо сначала остановите демон и повторите команду
```

Это **совет, а не гарантия взаимного исключения**: однократный TCP-опрос
адреса без блокировки и без рукопожатия с демоном. Между опросом и
применением остаётся окно, а проверяется `cfg.Listen` из **своего** `-config`,
а не то, что реально слушает работающий демон — если конфиги разошлись (демон
не перечитал изменившийся `listen:`, либо CLI вызван с другим `-config`),
проверка тихо промолчит и мутация выполнится параллельно с демоном. Файловой
блокировки между процессами в коде нет — решение сознательно отложено.

### Коды возврата

| Код | Значение |
|---|---|
| `0` | успех |
| `1` | внутренняя ошибка (в том числе — не загрузился конфиг) |
| `2` | некорректный ввод: пустое имя/id, недостающий аргумент, пустой пароль в `hash-password` |
| `3` | пир с таким id не найден |
| `4` | похоже, панель уже запущена и слушает тот же адрес |

Коды классифицируются по типу ошибки (`errors.Is`), а не по номеру команды —
скрипт вокруг CLI различает ситуации, не разбирая текст на stderr.

## Безопасность мутаций

Любая мутация, которая доходит до серверного конфига (`add`/`rm`/`disable`/
`enable`, правка имени или адреса пира, ротация ключей — из панели или из
CLI, где применимо), проходит одну и ту же последовательность
(`internal/issuer/apply.go`, раздел 6 спеки):

1. **снимок ДО** — `awg show <iface> dump` и `awg showconf <iface>`;
2. предварительная сверка: `[Interface]` файла на диске обязан совпадать со
   снимком устройства, иначе применение отменяется ещё до записи;
3. **изменение текста** — хирургически, ровно один блок `[Peer]` дописывается
   или вырезается; `[Interface]` и чужие блоки `[Peer]` задеть нельзя — в
   коде нет пути, которым это было бы возможно;
4. **бэкап** в `/var/lib/awg3panel/backups`, права `0600`, хранятся последние
   20, старые удаляются автоматически;
5. **атомарная запись** — временный файл рядом, `chmod 0600`, `rename`;
6. **`awg syncconf`** через результат `awg-quick strip`, переданный временным
   файлом — не аргументом и не подстановкой процесса, ключи не должны
   попадать ни в `/proc`, ни в общий `/tmp`;
7. **проверка постусловия** — сверка со снимком ДО: прежние пиры на месте,
   их `AllowedIPs` и `PresharedKey` не изменились, `latest handshake` не
   обнулился, device-параметры `[Interface]` идентичны, ожидаемое изменение
   произошло;
8. **откат при любом расхождении** — файл восстанавливается из памяти,
   `syncconf` повторяется, устройство сверяется со снимком ДО ещё раз; если
   откат не восстановил рабочее состояние, ошибка так и называется — «откат
   не удался», а не «изменения откачены».

Приватные ключи и PSK не попадают ни в логи, ни в тексты ошибок, ни в
HTTP-ответы 5xx — фильтруется даже сырой `stderr` внешних команд, поскольку
сам бинарь `awg` способен вернуть секрет в тексте своей ошибки.

Правка пира и ротация ключей проходят тот же инвариант, только шаг 3 (изменение
текста) у них разный: переименование и смена адреса заменяют существующий блок
`[Peer]` на месте, ротация убирает старый блок и дописывает новый на
освободившееся место — публичный ключ на устройстве это идентичность пира, и
смена ключа для инварианта равносильна замене одного пира другим, а не правке
существующего. Правка одних только клиентских оверрайдов (маршруты, DNS,
keepalive, MTU, endpoint, джиттер, `extra`) серверный конфиг не трогает
вовсе — блок `[Peer]` эти поля не хранит, менять там нечего. Мутация без
единого действительного изменения (например, `PATCH` с теми же именем и
адресом и без оверрайдов) возвращается до бэкапа и `syncconf` — риск на живом
устройстве не оправдан нулевым результатом.

## Правка параметров пира

У уже выпущенного пира редактируются: имя, адрес в туннеле и клиентские
параметры — DNS, что маршрутизировать в туннель, `PersistentKeepalive`, `MTU`,
`Endpoint`, джиттер `Jc`/`Jmin`/`Jmax` и произвольные дополнительные
client-side поля (`extra`) — то, что панель не знает по имени, но что нужно
для AWG 3.1 и будущих версий протокола.

**Два разных `AllowedIPs` — не опечатка, а два разных смысла одного и того же
имени поля:**

- **адрес в туннеле** — это `AllowedIPs` серверного блока `[Peer]`: единственный
  `/32`-адрес, по которому сервер узнаёт пакеты этого клиента. Смена этого поля —
  правка самого серверного конфига через тот же инвариант применения, что и у
  add/remove/disable (см. «Безопасность мутаций»); сессия у этого пира
  переустанавливается, у всех остальных — нет;
- **маршрутизировать в туннель** — это `AllowedIPs` **клиентского** конфига: что
  клиент отправляет через туннель, а что — напрямую (`0.0.0.0/0` — всё, более
  узкий список — только перечисленные сети). Это персональный оверрайд пира или
  умолчание интерфейса; серверного конфига оно не касается вовсе — поля для
  клиентских маршрутов в `[Peer]` попросту нет.

Спутать их — дорогая ошибка: правка не того поля либо не выпустит клиента дальше
одного адреса, либо не изменит то, что реально уходит в туннель.

Персональные значения хранятся как `overrides` в `peers.json`: отсутствие поля
означает «наследовать умолчание интерфейса», явное значение — «использовать
именно его», а явно пустая строка (там, где это осмысленно, например `dns: ""`)
— «этому пиру не нужно то, что есть в умолчаниях». Сбросить оверрайд назад в
наследование можно, отправив `null` — панель различает эти три состояния на
всём пути от формы до диска.

Валидация `extra` жёсткая, потому что содержимое печатается прямо в файл
клиентского конфига: имя поля — буква и до 15 букв/цифр, значение — без
переводов строк, скобок и пробелов по краям, а поле, у которого уже есть
отдельное место (`DNS`, `MTU`, `Jc`, ...), через `extra` не задать — иначе в
файле оказались бы две строки одного ключа с неопределённым приоритетом у
клиента.

## Ротация ключей

Действие «Ротировать ключи» выдаёт пиру новую пару ключей и новый
`PresharedKey`, сохраняя его `id`, имя и адрес — ссылки на пира и файл с его
приватным ключом (`keys/<id>.key`) остаются на том же месте. На сервере это не
правка пира, а замена одного другим: старый публичный ключ уходит из
серверного конфига, новый добавляется на то же место.

**Старый клиентский конфиг перестаёт работать немедленно** — сервер его больше
не узнаёт. Ротацию стоит делать, только когда новый конфиг (или QR) можно сразу
же передать владельцу устройства; панель возвращает его в том же ответе, что и
при первой выдаче.

Ротация — единственный способ вернуть в строй пира без известного приватного
ключа (заведённого вручную до установки панели либо с неудавшейся миграцией,
см. «Миграция ключей со старой установки»): после неё ключ панели известен, и
обычная выдача конфига начинает работать.

Если состояние `peers.json` разошлось с сервером (например, предыдущая ротация
успела заменить ключ на устройстве, но не успела записать это в `peers.json`),
повторная ротация отказывает явной ошибкой (HTTP 409) вместо того, чтобы молча
выпустить третий ключ или потерять метаданные пира. Специально открывать список
пиров ради починки не нужно и не стоит: расхождение согласуется само собой при
ближайшем обновлении списка (страница и так опрашивает его каждые 10 секунд) —
но при этом согласовании пир теряет `id`, дату выпуска и персональные
оверрайды: механизм самолечения не различает «пира убрали руками мимо панели» и
«прошлая ротация не дописалась», и в обоих случаях заводит запись заново, как
будто увидел пира впервые. Согласование, которое не выбрасывало бы запись, —
структурная починка, в этой версии панели её нет.

## Умолчания интерфейса

Редактируемые умолчания клиента (`endpoint`, маршруты, keepalive, DNS,
джиттер, `extra`) живут в `defaults.json` рядом с `peers.json` соответствующего
интерфейса, а не в `config.yaml`. Причина разделения: `config.yaml` — файл
развёртывания, его кладёт `install.sh`, лежит он в `/etc` с правами `600` и
содержит хеш пароля — переписывать его из сервиса значило бы терять комментарии
YAML при каждой правке и конфликтовать с идемпотентностью установщика.

`config.yaml` при этом остаётся **сидом**: секция `client` интерфейса
переносится в `defaults.json` при первом запуске и с этого момента больше не
перечитывается — правка `client.*` в уже работающей установке ничего не
меняет. Панель фиксирует это в журнале один раз за время работы процесса на
этот интерфейс, при первом реальном обращении к его умолчаниям — не при
старте: `defaults.json` читается лениво, из выпуска пира, ротации, сборки
конфига или самой вкладки «Умолчания», смотря что случится раньше. Дальше
умолчания правятся вкладкой «Умолчания» в вебе, без рестарта сервиса; они
применяются ко всем пирам, у которых по конкретному полю нет персонального
оверрайда.

Смена умолчаний, как и правка оверрайдов пира, серверного конфига не
касается — она видна в конфигах, которые клиенты получат при следующей выдаче.

## Обфускация, порт и MTU сервера

Правки серверного `[Interface]` панель не делает и в этой версии делать не
умеет — ни через веб, ни через CLI, ни как-то ещё: кода для такой записи в
бинаре нет (см. «Что делает и чего не делает», `CLAUDE.md`). Смена обфускации
(`S1..S4`, `H1..H4`, `HeaderProtectionKey`, `ContentPaddingAddition`), порта
(`ListenPort`) и MTU сервера — по-прежнему только руками, по SSH:
редактированием серверного конфига и `syncconf`/перезапуском интерфейса
напрямую. Панель об изменении узнаёт сама и ничего дополнительно настраивать
не нужно: `[Interface]` копируется из живого конфига при каждой выдаче
клиентского файла, поэтому новые конфиги подхватят правку сами.

## Миграция ключей со старой установки

До этой версии клиентский `.conf` собирался один раз при выпуске пира и лежал
файлом в `storage.client_configs` (`clients/<slug>.conf`) — приватный ключ
существовал только внутри этого файла. Теперь ключ хранится отдельно
(`storage.keys/<id>.key`, `0600`, каталог `0700`), а `.conf` собирается заново
при каждой выдаче — так правка обфускации или умолчаний не может молча сделать
уже выданные файлы негодными: файла, который мог бы устареть, больше нет.

Перенос происходит автоматически и лениво — не при каждом обращении к пиру, а
именно при попытке получить его конфиг или QR (просмотру списка пиров
приватный ключ не нужен, и миграция там не запускается): если `keys/<id>.key`
ещё нет, а `clients/<slug>.conf` есть, панель разбирает `.conf`, вычисляет
публичный ключ от найденного там `PrivateKey` и **сверяет его с публичным
ключом этого же пира в серверном конфиге**. Совпало — ключ переносится в
хранилище, а исходный `.conf` удаляется: держать один и тот же приватный ключ
в двух местах означает два места для утечки и два для расхождения. Не
совпало — перенос не выполняется, `keys/` остаётся пуст, `.conf` остаётся
нетронутым, а в журнал уходит ошибка с `id` пира и без единого ключа в
тексте: так испорченный или подменённый файл не станет тихим источником
нерабочего конфига.

Каталог `clients/` панель никогда не создаёт и никогда в него не пишет —
только читает на время миграции. По мере того как пиры получают обращение за
конфигом хотя бы один раз, каталог пустеет сам; когда в нём не осталось
файлов, его можно удалить вместе с полем `storage.client_configs` в
`config.yaml` — панель ничего не потеряет, потому что к этому моменту у
каждого пира с известным ключом он уже в `keys/`.

Пиры, для которых миграция не удалась или которые вообще заведены вручную до
установки панели (для них `storage.client_configs` ничего не даёт — файла для
переноса просто никогда не было), остаются полностью управляемыми — видны,
переименовываются, отключаются, удаляются, — но выдача конфига и QR отвечает
`404`, пока для такого пира не выполнена ротация ключей (см. «Ротация
ключей»).

## Известные ограничения

- **Пира без `PresharedKey` в серверном конфиге нельзя отключить.** Панель
  отказывает с кодом 400: сохранить в `peers.json` для обратного включения
  нечего, а вырезание блока `[Peer]` без PSK сделало бы пира невосстановимым.
  Такие пиры бывают, если заведены руками до установки панели.
- **Защита от одновременной работы CLI и демона — совет, а не блокировка**
  (см. раздел CLI).
- **`awg syncconf` сбрасывает параметры устройства, которых нет в
  применяемом файле** — измерено на AmneziaWG v3.0.20260730 (`awg set awg3
  fwmark 42` → `awg syncconf awg3 <strip>` → `awg show awg3 fwmark` = `off`).
  Поэтому панель отказывается применять мутацию, если на устройстве есть
  параметр `[Interface]`, отсутствующий в файле: сверьте файл с
  `awg showconf awg3` и исправьте расхождение вручную.
- **Конфиг без пиров и без завершающего перевода строки панель обслужить не
  может** — допишите перевод строки в конец файла.
